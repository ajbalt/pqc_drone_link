# SP 800-227 (Recommendations for KEMs)

**Summary**: Source summary of NIST SP 800-227 (September 2025): how to use a KEM such
as ML-KEM securely inside a protocol, including authentication, key confirmation,
post-processing of the shared secret, and combining KEMs into hybrids.

**Sources**: [sp-800-227](sources.md#sp-800-227)

**Last updated**: 2026-10-08

---

## What it is

FIPS 203 defines ML-KEM itself; SP 800-227 covers *using* any approved KEM in an
application. FIPS 203 points here for application requirements
([fips-203 §1.1](sources.md#fips-203)). Requirements are numbered: **RS** ones can be
tested by a validation lab, **RM** ones cannot
([sp-800-227 §2](sources.md#sp-800-227)).

## Takeaways for this project

1. A fresh ML-KEM key pair is needed for every handshake and every rekey (RS6).
2. ML-KEM alone gives no authentication. Our handshake must add it: PSK or signatures.
3. Key confirmation is recommended. The first successful AEAD packet counts, but an
   explicit confirmation would need HMAC/CMAC/KMAC, not Ascon.
4. Our KDF step is allowed (§4.3), and stricter than required.
5. A hybrid mode must combine the secrets *and* the ciphertexts. A plain KDF(K1, K2)
   is not IND-CCA-preserving.
